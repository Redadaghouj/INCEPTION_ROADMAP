Phase 00
Linux Processes & Daemons
2 days 3–4h/day Theory
Foundation. Docker is just isolated Linux processes. If you don't understand what PID 1 is and why it matters, you will write broken entrypoints and not know why containers keep dying.
Topics
PID 1 process tree signals (SIGTERM/SIGKILL) foreground vs daemon exec vs fork file permissions users & groups
Exercises
→ Write a shell script that spawns a child process. Use ps aux to find both PIDs and observe the tree. Then kill the parent — what happens to the child?
→ Read the "zombie process" and "orphan process" Wikipedia entries. Understand why init/PID 1 adopts orphans.
→ Run nginx directly in a terminal (foreground). Then run it as a daemon. Compare ps output. Understand what the daemon does differently.
Phase 01
Docker Core Concepts
2 days 3–4h/day Theory + Light Practice
Don't touch commands yet. Understand what Docker actually is. Image = filesystem snapshot. Container = isolated process running from that snapshot. Not a VM — no kernel, no boot sequence.
Subject constraint: You must build from the penultimate stable version of Alpine or Debian — not the latest. Check the current stable release, then use the one before it (e.g. if Debian 13 is stable, use Debian 12). The :latest tag is explicitly forbidden — always pin an explicit version tag like debian:bookworm or alpine:3.19.
Topics
images vs containers layers & union filesystem namespaces cgroups docker vs VM image registry docker run lifecycle
Exercises
→ Pull debian:bookworm (the penultimate stable at time of writing). Run it interactively. Install curl inside. Exit. Delete the container. Run again — curl is gone. Understand why.
→ Use docker inspect to find the container's PID on the host machine. Then run ps aux | grep [that PID] on the host. Confirm it's just a process.
→ Use docker image history debian:bookworm-slim to see its layers. Understand what each layer represents.
Phase 02
Dockerfile — Writing Images
3 days 4h/day Practice-heavy
The most important skill in this project. You build all three images yourself — no ready-made pulls. Focus hardest on CMD vs ENTRYPOINT and how to write an entrypoint script that starts your service as PID 1 without forbidden hacks.
Topics
FROM / RUN / COPY WORKDIR / EXPOSE CMD vs ENTRYPOINT exec form vs shell form exec "$@" pattern ARG vs ENV layer caching .dockerignore
Exercises
→ Day 1: Write a Dockerfile for a plain nginx from debian:bookworm-slim. No config yet — just install nginx and make it start as PID 1. Verify with docker exec <id> ps aux that nginx is PID 1 inside.
→ Day 2: Add an entrypoint shell script. The script does some setup, then exec "$@" to hand control to nginx. Understand why exec is critical here (signal forwarding, PID 1 replacement).
→ Day 3: Intentionally break the Dockerfile 3 different ways (wrong CMD form, missing exec, wrong base). Debug each. Knowing how it breaks teaches you more than getting it right the first time.
Trap: Shell form of CMD/ENTRYPOINT (e.g., CMD "nginx -g...") wraps the command in /bin/sh -c, meaning nginx is NOT PID 1 — sh is. Signals won't reach nginx. Always use exec form: CMD ["nginx", "-g", "daemon off;"]
Banned hacks (explicit subject prohibition): Your containers must NOT be started with an infinite loop or a placeholder command. The following are explicitly forbidden as entrypoints or CMD: tail -f, bash, sleep infinity, while true. If you're using any of these to "keep a container alive," you don't understand PID 1 yet — go back and fix it.
Phase 03
Docker Compose + Network + Volumes
2 days 3–4h/day Theory + Practice
Compose is just orchestration YAML. But the network and volumes sections are what the evaluator will grill you on. Understand exactly why wordpress resolves to the WordPress container's IP inside the Docker network.
Hard bans in Compose: network: host, --link, and links: are all forbidden. You must define a custom bridge network and use service names for DNS. The network key must be explicitly present in your docker-compose.yml — an implicit default network is not acceptable.
Volume path requirement: Both named volumes must store their data under /home/<your_login>/data on the host machine. You configure this in the Compose driver_opts. The evaluator will check this path exists and contains your data.
Makefile is mandatory: A Makefile at the repo root must wrap your entire workflow. At minimum it must call docker compose up --build (and down/clean targets). The evaluator runs make — if it doesn't build and launch everything automatically, you fail before they even look at your containers.
VM + domain setup (do this early, not at test time): The project runs on a VM. Your domain <login>.42.fr must resolve to your VM's local IP. Add the entry to /etc/hosts on the VM: 127.0.0.1 <login>.42.fr. Also confirm your VM's shared folders or SSH are set up so you can work comfortably. Students who skip this until Phase 07 lose hours at the worst moment.
Topics
services / networks / volumes depends_on restart: unless-stopped bridge network service DNS resolution named volumes bind mount vs named volume env_file image name = service name
Exercises
→ Write a Compose file with 2 services: a basic nginx and a debian container. From inside the debian container, curl http://nginx using the service name as hostname. Confirm DNS resolution works.
→ Add a named volume. Write a file into it from one container. Delete that container. Spin a new one — confirm the file is still there. This is the volume persistence mental model.
→ Simulate a crash: docker kill <container>. Observe it restart automatically due to restart: unless-stopped. Check with docker ps.
Service Implementation
Phase 04
The Three Services
5 days 4–5h/day Heaviest Phase
This is where most of the project time goes. Do them in order: MariaDB first (no dependencies), then WordPress+PHP-FPM (depends on DB), then NGINX (depends on both). One wrong entrypoint here breaks everything downstream.
MariaDB (Day 1–2)
mysql_install_db init script via entrypoint CREATE USER / GRANT mysqld as PID 1 port 3306
WordPress + PHP-FPM (Day 3–4)
php-fpm vs php-apache FastCGI protocol wp-config.php WP-CLI for automation listen on 9000 two DB users required
Admin username restriction: The WordPress administrator account's username cannot contain "admin", "Admin", "administrator", or "Administrator" in any form — including admin-123, wp_admin, etc. The evaluator will check this in the DB. Set it to something like your login name via WP-CLI during container init.
NGINX (Day 5)
server block fastcgi_pass wordpress:9000 ssl_certificate TLSv1.2 / TLSv1.3 only port 443 only self-signed cert with openssl
Exercises
→ MariaDB: Write an entrypoint script that initializes the DB on first boot only (check if /var/lib/mysql/mysql exists before running init). Get this wrong and every restart re-initializes and wipes data.
→ PHP-FPM: After building your WordPress container, exec into it and confirm php-fpm is listening on port 9000 with ss -tlnp. Then from nginx container, telnet to wordpress:9000 to verify reachability.
→ NGINX: Generate a self-signed cert with openssl (understand what CN and SAN fields mean). Configure nginx to reject TLS 1.0 and 1.1 explicitly. Verify with openssl s_client -connect yourdomain:443 -tls1 — should fail.
→ Full stack test: bring everything up cold (docker compose up --build), access your domain, complete WordPress setup. Then docker compose down and back up — confirm all data persisted via volumes.
Trap (MariaDB): The init script must run mysqld in the background, execute your SQL setup, then bring mysqld to foreground as PID 1. Sequence matters — most people get this wrong on first try and lose a full day debugging.
Phase 05
Secrets, Env Vars & Security
1 day 3–4h/day Critical
Any credential found in your git history = instant failure. This is not optional. Understand the difference between .env (convenience) and Docker secrets (actual security). The subject requires both patterns.
Required repo structure: Your project must follow this layout exactly — evaluators check it:

Makefile (root)
secrets/credentials.txt — WordPress admin credentials
secrets/db_password.txt
secrets/db_root_password.txt
srcs/docker-compose.yml
srcs/.env
srcs/requirements/nginx/ (Dockerfile + conf + tools)
srcs/requirements/wordpress/
srcs/requirements/mariadb/

The secrets/ folder must be in your .gitignore. All three secret files must exist locally but never appear in git history.
Topics
.env file structure env_file in Compose secrets/ folder Docker secrets mechanics /run/secrets/ at runtime .gitignore for secrets no passwords in Dockerfiles
Exercises
→ Audit your Dockerfiles and Compose file: grep for any hardcoded password strings. There should be zero. If you find one, you already failed that criterion.
→ Implement Docker secrets: put DB password in secrets/db_password.txt. Read it in your entrypoint script via cat /run/secrets/db_password. Confirm the secret is not visible in docker inspect env vars.
→ Run git log --all -p | grep -i password on your repo. If anything shows up, you need to purge history with git filter-branch or BFG. Do this before first push.
Phase 06
Documentation
2 days 3h/day Writing
The subject requires three separate documentation files. Most guides don't mention this. Write them while the project is still fresh — not after. The four comparisons in the README are evaluation material and evaluators specifically ask about them.
README first line (exact requirement): The very first line of your README must be italicized and read: This project has been created as part of the 42 curriculum by <your_login>. — this is checked. A missing or wrong first line is a documentation failure.
Required Files
README.md USER_DOC.md DEV_DOC.md
Four Required Comparisons in README
VMs vs Docker Secrets vs Env Vars Docker Network vs Host Network Named Volumes vs Bind Mounts
What each file needs
→ USER_DOC.md: How to start/stop the project, access the site and admin panel, locate credentials, check services are running.
→ DEV_DOC.md: Setup from scratch, build + launch via Makefile and Compose, container/volume management commands, where data persists.
→ README must also describe AI usage: which tasks, which parts of the project. Be honest — vague answers get questioned.
Phase 07
Testing & Hardening
2 days 4h/day Validation
You are not done when it runs once. You're done when it survives destruction and still works perfectly. The evaluator follows a fixed script — know every step of it before they arrive.
⚠ Evaluator's first command — run this yourself first
docker stop $(docker ps -qa); docker rm $(docker ps -qa); docker rmi -f $(docker images -qa); docker volume rm $(docker volume ls -q); docker network rm $(docker network ls -q) 2>/dev/null
Then they run make. No cached images, no volumes, no dangling networks. Run this yourself before eval and time the cold build.
Infrastructure Checks
→ docker images — each image name must match its service name in docker-compose.yml exactly. inception-nginx or myproject_nginx will fail. The eval sheet checks this explicitly.
→ docker compose ps — all three containers must show as running. Any "Exit" or "Restarting" state = fail. Know what healthy output looks like before the evaluator runs it.
→ docker network ls — your custom network must be visible. The evaluator confirms it, then asks you to explain how Docker networking works.
→ docker volume ls then docker volume inspect <name> — the evaluator looks for /home/<login>/data/ in the Mountpoint. Do this for both volumes and confirm the path appears.
Access & TLS Checks
→ curl http://<login>.42.fr must be refused. https://<login>.42.fr must serve the WordPress site — not the installation wizard. WordPress must be fully configured by your entrypoint, not manually.
→ TLS: openssl s_client -connect <login>.42.fr:443 -tls1_2 must succeed. -tls1 and -tls1_1 must fail. Self-signed cert warning is fine — the evaluator expects it.
WordPress Functional Checks
→ Log in as the non-admin user → post a comment. The evaluator does this. Ensure the second user has comment permissions and credentials are in secrets/credentials.txt.
→ Log in as admin → edit a page → verify the change shows on the live site. Admin username must not contain "admin" in any form. Know the path: WP Admin → Pages → Edit → Update.
→ DB login demo — know this cold: docker exec -it <mariadb> mysql -u <user> -p <dbname>, then SHOW TABLES; and SELECT user_login FROM wp_users;. The evaluator asks you to demonstrate this.
Persistence Test — VM Reboot
→ The evaluator reboots the virtual machine. After reboot, they run make again and verify the WP page edit they made is still there. This is not docker compose down/up — it's a full VM restart. Test this yourself before eval day.
Audit & Question Prep
→ Entrypoint script audit: if your ENTRYPOINT calls a script, the evaluator reads it. No background processes — nginx & bash or mysqld & sleep are banned even inside scripts. Must end with exec "$@" or directly exec the service.
→ Credential audit: docker inspect <container> | grep -i password on all three containers — must return nothing. Then git log --all -p | grep -i password one last time.
→ Say these out loud: "How does Docker differ from a VM?" · "How does docker compose work?" · "Why custom network instead of host?" · "Where does WP data live on disk?" · "What does exec do in your entrypoint?" · "Why TLSv1.2/1.3 only?" · "Walk me through your MariaDB init sequence."
→ Live modification drill: the eval sheet warns the evaluator may request a small live change. Practice it — change the nginx server header, update the WP site title via WP-CLI — in under 5 minutes from scratch. If you can't, you are not ready.
Bonus — only after mandatory is perfect
Bonus
Extended Services
3–4 days 3–4h/day Optional
Each bonus is its own Dockerfile + container. Do them in this order — Redis is the most valuable to understand, static site is the fastest win, Adminer is trivial, FTP is the annoying one. The evaluator awards 1 point per working bonus and will ask you to justify your custom service choice.
01 — Redis
Install redis-cache WP plugin via WP-CLI in the WordPress entrypoint. Set WP_REDIS_HOST env var. Understand what object caching actually does — evaluator will ask.
02 — Static Site
Easiest bonus. Serve via nginx on a different port (e.g. 8080). Can be your portfolio. No PHP allowed. Needs its own Dockerfile.
03 — Adminer
Single PHP file, tiny image. Serve on port 8888. Connects to MariaDB. Barely any config — fastest bonus to ship. Good sanity check for your DB setup too.
04 — FTP Server
Use vsftpd. Point it to the WordPress named volume mount path. Annoying to configure passive mode correctly — read the vsftpd.conf docs carefully before starting.
05 — Custom Service (your choice)
Any service you find useful. You must justify your choice during the defense — have a clear, technical answer ready. Suggestions: Fail2ban, cAdvisor, a monitoring exporter, a mail relay. Pick something you actually understand.
Warning: Bonus is evaluated only if mandatory is 100% complete with zero malfunctions. If mandatory fails at any point during eval, bonus points are ignored entirely. Don't touch bonus until every mandatory test passes cleanly on a cold build.
